# 多智能体项目协作与共享镜像规范


> 状态：当前协作基线
> 适用范围：任何同时使用产品侧智能体、工程侧智能体、本地代码仓库与云端共享目录的软件或数字产品项目
> 目标：让不同智能体围绕同一套项目状态协作，把高能力模型用于思考，把文件系统用于传输，把 Git 用于版本历史，把长期文档用于保存事实。


---


## 1. 核心原则


这套协作模式不是某一个项目专属流程，而是一套可以直接复用到其他项目的通用方法。


一句话定义：


> 云端共享目录保存可协作的完整项目镜像；本地仓库保存工程权威状态；交接文档传递“发生了什么和下一步做什么”；文件系统负责实际同步；Git 负责版本历史。


需要始终区分四件事：


1. 项目事实：代码、正式文档、测试、设计资产、验收证据等。
2. 共享状态：不同智能体当前都需要访问的最新项目文件。
3. 交接语义：本轮改了什么、接收方要读什么、下一步要做什么。
4. 版本历史：提交、分支、标签、发布、回滚。


这四件事分别由不同机制负责，不要混在一起。


---


## 2. 推荐角色


### 2.1 产品侧智能体


主要负责：


- 产品规划；
- 需求分析；
- 产品需求文档；
- 产品交接；
- 交互与信息架构；
- AI 产品行为设计；
- 产品决策整理；
- 跨文档一致性检查；
- 产品评审；
- 面向产品负责人的长文档表达。


产品侧智能体可以读取最新代码、测试、配置与工程证据，但默认不直接修改生产代码。


### 2.2 工程侧智能体


主要负责：


- 代码仓库分析；
- 技术设计；
- 实现可行性判断；
- 编码与重构；
- 脚本与自动化；
- 测试；
- 持续集成；
- 调试；
- 运行时分析；
- 工程证据；
- Git 操作。


生产代码的修改权默认属于工程侧。


### 2.3 产品负责人


主要负责：


- 产品目标；
- 范围和边界；
- 关键产品决策；
- 里程碑验收；
- 产品影响型技术冲突裁决；
- 最终发布授权。


产品负责人不应长期承担：


- 在不同智能体之间搬文件；
- 手工打包和解压交接包；
- 反复复制长提示词；
- 人工判断哪一份文档才是最新；
- 为了同步而逐个上传或下载项目文件。


---


## 3. 云端共享目录的定位


云端共享目录是“共享工作状态 / 共享项目镜像”。


它不是：


- Git 的替代品；
- 本地代码仓库的替代品；
- 版本发布系统；
- 只给某一个智能体看的阅读副本；
- 每轮重新生成的临时交接包。


推荐让云端目录结构与本地项目保持一致。


如果使用 Google Drive for desktop、OneDrive、Dropbox 或其他提供本地挂载目录的云盘，优先直接利用它们暴露出来的本地文件系统目录。


---


## 4. 什么叫完整同步


目标不是磁盘逐字节克隆，而是“协作完整的项目镜像”。


凡是对产品、工程、设计、测试、验收、恢复、历史追溯或后续协作有价值，并且适合进入共享环境的项目文件，默认都应该同步。


不要把“只同步 Git 已跟踪文件”当成唯一规则。


安全、有效、具有项目价值的未跟踪文件也可以进入共享镜像。


---


## 5. 默认同步范围


默认同步：


- 源代码；
- 测试；
- 脚本；
- 配置；
- lockfile；
- schema / contract；
- 正式 Markdown 文档；
- 设计资产；
- 脱敏后的测试夹具；
- 可共享的截图；
- 正式交接文件；
- 历史产品与工程文档；
- 发布与验收产物；
- 对评审、测试、恢复或交付有实际价值的生成文件；
- 其他安全且有协作价值的项目文件。


以下内容不要因为“是生成文件”就自动排除：


- dist/；
- 构建产物；
- 生成报告；
- 分析包；
- 发布包；
- 验收证据。


是否同步应按“有没有协作价值”判断。


---


## 6. 默认不同步范围


默认排除：


- .git/；
- node_modules/；
- 真实 .env；
- API Key；
- token；
- credential；
- 浏览器或 QA profile；
- cookie；
- session；
- MFA 后的会话状态；
- 私有原始业务数据；
- 含个人或业务隐私的原始截图；
- 原始推理轨迹；
- 纯缓存；
- 纯临时文件；
- 其他不适合进入共享环境的机器内部状态。


原因：


### .git/


Git 自己已经负责提交历史、对象、引用、锁和回滚。把 .git/ 放进云盘双向同步没有必要，而且在 Git 正在写入时可能出现冲突或损坏。


### node_modules/


体积大、小文件数量多、可通过 lockfile 重建，并且可能包含平台相关二进制。同步它通常只会拖慢系统。


### .env、凭据和会话状态


它们属于安全边界，不应该进入共享项目镜像。


### 私有原始数据


共享镜像会扩大可访问范围。只有经过脱敏、确认适合协作的数据才应该进入。


### 纯缓存和临时文件


它们变化频繁、可重新生成，而且会制造大量无意义的文件变化。


---


## 7. 文件同步与文件阅读是两件事


这是整套方法最重要的成本原则之一。


智能体不需要为了同步一个文件而阅读它的正文。


文件系统可以只根据：


- 路径；
- 大小；
- 修改时间；
- hash；
- 文件是否存在；


判断是否需要复制。


例如一个项目有 500 个文件，只有 8 个发生变化：


扫描 500 个文件 → 发现 8 个不同 → 实际复制 8 个文件。


这里的扫描是操作系统或同步工具完成的，不等于模型阅读 500 个文件。


因此：


> 文件同步成本与模型上下文成本应彻底分离。


模型只阅读真正需要理解的文件。


---


## 8. 优先使用文件系统原生同步


如果云盘已经提供本地挂载目录，优先使用系统已有工具：


- rsync；
- cp；
- diff；
- find；
- shasum；
- Git 自带的状态与差异命令。


不需要为了这套协作方式额外开发一个专用同步程序。


其中 rsync 可以理解为“会自动比较差异的复制”。


推荐逻辑：


逻辑上同步整个项目 → 系统自动比较 → 物理上只复制变化的文件。


因此可以同时获得：


> 完整项目状态 + 增量传输成本。


只有在长期实践证明同步参数频繁出错、排除规则长期不一致、多机器路径管理复杂、冲突处理不稳定或多个项目需要统一自动化时，才考虑开发专用同步工具。


在这些问题出现之前，不要过度设计。


---


## 9. 同步方向与修改权限


### 9.1 物理文件层面


项目文件可以：


云端共享镜像 ↔ 本地项目目录


双向同步。


### 9.2 修改权限层面


物理双向同步不等于所有智能体都可以修改所有文件。


推荐权限：


- 产品侧智能体：产品文档的主要维护者；
- 工程侧智能体：生产代码的主要维护者；
- 两侧都可以读取完整项目镜像；
- 混合文档由最接近事实的一侧提供事实，再由负责最终表达的一侧整理。


原则：


> 同步方向与修改权限分离。


---


## 10. 每次交接使用两个长期文件


不要每次新建一份交接文档。


推荐在项目中固定保存：


docs/collaboration/CHATGPT_TO_CODEX_HANDOFF.md
docs/collaboration/CODEX_TO_CHATGPT_HANDOFF.md


名称可以根据实际使用的智能体调整，但建议保持“发送方 → 接收方”的方向明确。


规则：


- 产品侧只更新“产品侧 → 工程侧”文件；
- 工程侧只更新“工程侧 → 产品侧”文件；
- 接收方读取对应文件；
- 每次新交接直接覆盖自己的长期交接文件；
- 不需要建立不断增长的临时 Handoff 文件。


---


## 11. 交接文件不是历史档案


长期交接文件的定位是：


> 当前收件箱，而不是历史档案。


它只负责告诉接收方：


- 当前处于什么阶段；
- 本轮发生了什么；
- 哪些文件发生变化；
- 哪些文件需要重点阅读；
- 同步方向是什么；
- 下一步任务是什么；
- 有什么约束；
- 验收标准是什么；
- 是否存在阻塞或冲突。


真正需要长期保存的事实应进入：


- 产品需求文档；
- 决策日志；
- 技术设计；
- AI 设计；
- 工程报告；
- 验收记录；
- Git history；
- 其他正式文档。


不要让 Handoff 变成第二套历史数据库。


---


## 12. 长期交接文件的固定结构


建议每份 Handoff 至少包含：


- Handoff ID；
- Updated At；
- From；
- To；
- Current Stage；
- Status；
- Source Git HEAD；
- 本轮发生了什么；
- 发生变化的文件；
- 接收方需要重点阅读；
- 同步要求；
- 下一步任务；
- 不要做什么；
- 验收要求；
- 已知问题 / 冲突；
- 其他说明。


Status 建议使用：


- READY；
- IN_PROGRESS；
- WAITING；
- BLOCKED。


接收方只执行最新且状态为 READY 的交接。


---


## 13. Handoff Prompt 可以缩短到一句话


当长期 Handoff 已经成为正式协作入口后，不再需要每轮复制长提示词。


产品侧交给工程侧时，只需要：


> 读取最新的“产品侧 → 工程侧” Handoff，按照其中指令继续。


工程侧交给产品侧时，只需要：


> 读取最新的“工程侧 → 产品侧” Handoff，按照其中指令继续。


真正的完整指令放在 Handoff 文件内部。


这可以显著减少人工复制、提示词重复、上下文丢失、错版本风险和交接时的 token 消耗。


---


## 14. Handoff 与同步的职责不同


Handoff 负责“语义：发生了什么，下一步要做什么”。


文件同步负责“物理：哪些文件需要从一边复制到另一边”。


不要让 Handoff 承担文件传输，也不要让 rsync 承担项目理解。


可以理解为：


- Handoff = 发生了什么；
- 文件系统同步 = 哪些文件不一样；
- 正式文档 = 事实是什么；
- Git = 历史发生过什么。


---


## 15. 产品侧 → 工程侧流程


产品侧完成工作
→ 更新云端共享镜像中的正式文档
→ 更新“产品侧 → 工程侧”长期 Handoff
→ 产品负责人只发送一句“读取最新 Handoff”
→ 工程侧读取 Handoff
→ 工程侧先同步云端镜像 → 本地
→ 只重点阅读 Handoff 指定的文件
→ 开始工程工作。


同步时优先让系统对整个项目树做差异比较，而不是让模型逐个判断。


---


## 16. 工程侧 → 产品侧流程


工程侧完成开发和测试
→ 更新“工程侧 → 产品侧”长期 Handoff
→ 本地项目 → 云端共享镜像
→ 云盘客户端自动上传
→ 产品负责人只发送一句“读取最新 Handoff”
→ 产品侧读取 Handoff
→ 产品侧只重点阅读发生变化的文件
→ 产品评审或下一轮规划。


---


## 17. 增量同步与全量同步


对于中小项目，直接“同步整个项目树”通常也可以。


需要区分：


- 逻辑全量同步：让两边项目状态对齐；
- 物理全量复制：不比较差异，把所有文件重新写一遍。


推荐做法：


> 逻辑上每次都可以同步整个项目，物理上优先只复制差异。


rsync 很适合做这件事。


如果项目很小，普通复制的成本也很低，可以优先保持流程简单。


不要为了追求理论上的最优增量而增加大量复杂性。


---


## 18. 冲突保护


同步前需要避免盲覆盖。


至少检查：


- 本地是否有未提交修改；
- 云端同名文件是否也发生变化；
- 文件 hash 是否不同；
- 当前 Git HEAD；
- Handoff 指定的同步方向。


如果双方都改了同一份文件：


> 停止自动覆盖，报告同步冲突。


再由高能力模型或产品负责人决定合并、保留本地、保留云端或手工处理。


删除操作尤其需要谨慎。


不要默认使用无条件 destructive --delete。


---


## 19. 安全与隐私检查


同步前优先使用确定性规则：


文件路径与类型 → 排除规则 → secret scan → privacy rule → 同步 → 校验。


不要让高能力模型为了判断“要不要同步”而逐份阅读整个项目。


如果发现 secret、token、credential 或 private raw data，停止同步对应内容，并报告路径和原因，但不要把敏感内容本身输出到日志或聊天。


---


## 20. Git 的职责


Git / GitHub 负责：


- diff；
- commit；
- branch；
- history；
- rollback；
- tag；
- release；
- public repository。


云端共享目录不替代 Git。


推荐理解：


日常共享工作状态 → 云端共享镜像。
版本与历史 → Git / GitHub。


不需要为了让产品侧智能体看到最新文件而频繁做无意义 commit。


---


## 21. 文档与事实治理


所有长期事实应该进入它真正所属的文档。


推荐遵循：


> 一个事实，一个权威归属。


例如：


- 产品要求 → 产品需求文档；
- 当前 AI 行为 → AI 设计；
- 技术结构 → 技术设计；
- 为什么这样决定 → 决策日志；
- 已实现和已测试什么 → 工程报告；
- 当前交接 → Handoff；
- 版本历史 → Git。


Handoff 不复制长期文档正文，只引用需要重点阅读的文件。


---


## 22. 新项目如何直接复用


任何新项目要采用本模式，只需要：


1. 建立 canonical local repo；
2. 建立云端项目文件夹；
3. 启用云盘桌面客户端；
4. 确定本地挂载路径；
5. 第一次建立协作完整镜像；
6. 放入本规范；
7. 在项目 Agent 规则入口中引用本规范；
8. 建立两个长期 Handoff 文件；
9. 确定默认排除规则；
10. 开始第一次产品侧 → 工程侧交接。


不需要：


- 新建同步服务；
- 新建数据库；
- 新建 daemon；
- 新建专用 API；
- 每轮打 ZIP；
- 每轮复制长 Prompt；
- 每轮重新上传整个仓库。


---


## 23. 推荐的项目规则入口


项目可以在 AGENTS.md 或等价规则文件中只写一个短入口：


> 跨智能体协作、云端共享镜像、文件同步与 Handoff 必须遵循项目中的《多智能体项目协作与共享镜像规范》。大规模文件传输优先使用云盘桌面客户端与本地文件系统工具，不使用高能力模型逐文件搬运。


详细规则只保留在本规范中，避免多个文件复制相同规则。


---


## 24. 什么时候需要人工介入


自动流程可以自行处理：


- 文件比较；
- 无冲突同步；
- 普通增量复制；
- hash 校验；
- 读取 Handoff；
- 自动测试。


需要人工介入：


1. 产品范围或边界变化；
2. 产品影响型技术冲突；
3. 双方修改同一文件产生冲突；
4. 关键测试失败且无法自行解决；
5. 发布或重大里程碑验收；
6. 安全、隐私或 secret 风险。


---


## 25. 最终工作模型


最终把整个协作理解成四层：


第一层：正式项目事实
代码 / 文档 / 测试 / 设计 / 证据


第二层：共享项目状态
云端共享镜像


第三层：当前交接
两个长期 Handoff


第四层：版本历史
Git / GitHub


不同智能体之间不再“搬一份上下文”，而是围绕同一个项目状态协作。


---


## 26. 最终原则


1. 一个项目状态：本地与云端代表同一个协作项目。
2. 完整但不盲目：尽可能同步有协作价值的文件。
3. 秘密不共享：secret、credential、session、private raw data 留在安全边界内。
4. 文件系统做传输：优先使用云盘桌面客户端与 rsync 等现成工具。
5. 模型不当搬运工：模型负责判断，不负责逐文件网络传输。
6. 逻辑全量，物理增量：每轮可以要求整个项目对齐，底层只复制真正变化的文件。
7. 同步与阅读分离：复制文件不等于把文件内容放进模型上下文。
8. 同步方向与修改权限分离：文件可双向同步，但代码和产品文档有不同维护责任。
9. 两个长期 Handoff：一个方向一个文件，每次覆盖当前状态。
10. Handoff 是收件箱，不是档案馆。
11. Prompt 极简化：交接时只需要“读取最新 Handoff 并继续”。
12. Git 管历史，云盘管共享状态，正式文档管事实。
13. 先用简单方法：没有真实痛点前，不开发新的同步基础设施。
14. 发生冲突时停止盲覆盖。
15. 让人只处理真正需要人的决策。


---


## 27. 核心结论


这套模式的本质不是“把项目备份到云盘”。


它真正解决的是：


> 如何让多个 AI Agent 围绕同一个项目持续协作，而不反复搬运上下文、文件和长提示词。


最佳分工是：


> 高能力模型做高价值思考，文件系统做文件传输，长期文档保存事实，Handoff 保存当前交接，Git 保存历史。


---


## 28. 如何进入这个协作闭环


这套协作模式需要区分“第一次建立项目”与“之后每一次进入项目”。


### 28.1 第一次建立新项目：需要一次启动提示


新项目第一次采用这套模式时，需要一条一次性的启动提示，用来完成以下初始化：


1. 找到或建立本地代码仓库；
2. 找到或建立云端共享项目目录；
3. 确认云盘桌面客户端的本地挂载路径；
4. 将本规范放入项目的长期文档目录；
5. 在项目的 Agent 规则入口中登记本规范；
6. 建立两个长期 Handoff 文件；
7. 建立第一次协作完整镜像；
8. 明确默认同步排除项；
9. 明确产品侧和工程侧的修改权限；
10. 完成第一次交接。


这条启动提示只用于“安装协作系统”，不应在每轮工作中重复。


推荐的新项目启动提示可以非常短：


> 为这个项目启用项目内《多智能体项目协作与共享镜像规范》。先建立云端共享镜像和本地同步关系，在 Agent 规则入口中登记协作规范，并创建产品侧 → 工程侧、工程侧 → 产品侧两个长期 Handoff。完成初始化后，所有后续交接都从长期 Handoff 进入，不再使用长交接 Prompt。


### 28.2 项目已经初始化：从 Agent 规则入口进入


项目一旦完成初始化，工程侧智能体每次进入仓库时，都应该先读取项目的 Agent 规则入口，例如：


`AGENTS.md`


其中只需要保留一条稳定入口规则：


> 开始跨智能体协作任务前，先读取项目中的《多智能体项目协作与共享镜像规范》，然后读取“发送给自己”的长期 Handoff；如果 Handoff 状态为 READY，则按其中要求完成同步并继续工作。


详细协作规则不要复制到 AGENTS.md，避免多个规则源漂移。


### 28.3 产品侧智能体的入口


如果产品侧智能体不会自动读取仓库中的 AGENTS.md，应在该产品侧工作空间、项目说明或第一次启动提示中加入一条长期入口：


> 每次开始项目工作前，先从云端共享项目目录读取《多智能体项目协作与共享镜像规范》，再读取“工程侧 → 产品侧”长期 Handoff。只有状态为 READY 的最新 Handoff 才作为本轮交接入口。


这条规则可以放进 ChatGPT Project Instructions、团队工作区说明或其他等价的持久项目设置中。


### 28.4 日常交接不再需要长 Prompt


完成初始化以后，正常交接只需要一句话：


产品侧 → 工程侧：


> 读取最新的“产品侧 → 工程侧” Handoff，按照其中指令继续。


工程侧 → 产品侧：


> 读取最新的“工程侧 → 产品侧” Handoff，按照其中指令继续。


如果接收方已经通过持久项目规则自动知道 Handoff 位置，甚至可以进一步缩短为：


> 读取最新 Handoff，继续。

## 29. 每次新会话的标准启动顺序


无论是哪一侧，进入一个已经初始化的项目时，标准顺序都是：


1. 读取项目规则入口；
2. 读取本协作规范；
3. 确定自己是产品侧还是工程侧；
4. 读取“发送给自己”的长期 Handoff；
5. 检查 Handoff ID、更新时间、状态和源项目状态；
6. 如果状态不是 READY，不自行猜测下一步；
7. 如果状态是 READY，先完成需要的文件同步；
8. 只重点读取 Handoff 指定的文件；
9. 开始本轮正式工作；
10. 工作完成后更新“自己发送给对方”的长期 Handoff。


这形成一个稳定闭环：


规则入口
→ 协作规范
→ 入站 Handoff
→ 同步
→ 工作
→ 出站 Handoff
→ 对方的规则入口。

## 30. 为什么仍然保留启动 Prompt


长期 Handoff 可以消灭“每轮长 Prompt”，但不能完全消灭“第一次入口”。


原因是：


- 一个全新的 Agent 还不知道项目在哪里；
- 它还不知道协作规范在哪里；
- 它还不知道自己应该读取哪个 Handoff；
- 一个全新的项目也还没有建立共享镜像和长期 Handoff。


因此最佳设计不是“永远不要 Prompt”，而是：


> **一次性 Bootstrap Prompt + 持久 Agent 入口 + 两个长期 Handoff + 日常一句话交接。**


其中：


- Bootstrap Prompt 负责安装协作系统；
- Agent 规则入口负责告诉智能体从哪里开始；
- Collaboration Model 负责解释整套规则；
- Handoff 负责当前任务；
- 云端镜像负责共享文件状态；
- Git 负责历史。


完成第一次初始化后，后续绝大多数交接都不再需要复制长 Prompt。
