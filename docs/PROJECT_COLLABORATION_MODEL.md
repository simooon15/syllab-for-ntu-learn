# 多智能体项目协作与共享镜像规范




> 状态：当前协作基线
> 适用范围：任何同时使用产品侧智能体、工程侧智能体、本地代码仓库与云端共享目录的软件或数字产品项目
> 目标：让不同智能体围绕同一套项目状态协作，把高能力模型用于思考，把文件系统用于传输，把 Git 用于版本历史，把长期文档用于保存事实。




---




## 1. 核心原则




这套协作模式不是某一个项目专属流程，而是一套可以直接复用到其他项目的通用方法。




一句话定义：




> 云端共享目录保存可协作的完整项目镜像；本地仓库保存工程权威状态；交接文档传递“发生了什么和下一步做什么”；文件系统负责实际同步；Git 负责版本历史。




需要始终区分四件事：




1. 项目事实：代码、正式文档、测试、设计资产、验收证据等。
2. 共享状态：不同智能体当前都需要访问的最新项目文件。
3. 交接语义：本轮改了什么、接收方要读什么、下一步要做什么。
4. 版本历史：提交、分支、标签、发布、回滚。




这四件事分别由不同机制负责，不要混在一起。




---




## 2. 推荐角色




### 2.1 产品侧智能体




主要负责：




- 产品规划；
- 需求分析；
- 产品需求文档；
- 产品交接；
- 交互与信息架构；
- AI 产品行为设计；
- 产品决策整理；
- 跨文档一致性检查；
- 产品评审；
- 面向产品负责人的长文档表达。




产品侧智能体可以读取最新代码、测试、配置与工程证据，但默认不直接修改生产代码。




### 2.2 工程侧智能体




主要负责：




- 代码仓库分析；
- 技术设计；
- 实现可行性判断；
- 编码与重构；
- 脚本与自动化；
- 测试；
- 持续集成；
- 调试；
- 运行时分析；
- 工程证据；
- Git 操作。




生产代码的修改权默认属于工程侧。




### 2.3 产品负责人




主要负责：




- 产品目标；
- 范围和边界；
- 关键产品决策；
- 里程碑验收；
- 产品影响型技术冲突裁决；
- 最终发布授权。




产品负责人不应长期承担：




- 在不同智能体之间搬文件；
- 手工打包和解压交接包；
- 反复复制长提示词；
- 人工判断哪一份文档才是最新；
- 为了同步而逐个上传或下载项目文件。




---




## 3. 云端共享目录的定位




云端共享目录是“共享工作状态 / 共享项目镜像”。




它不是：




- Git 的替代品；
- 本地代码仓库的替代品；
- 版本发布系统；
- 只给某一个智能体看的阅读副本；
- 每轮重新生成的临时交接包。




推荐让云端目录结构与本地项目保持一致。




如果使用 Google Drive for desktop、OneDrive、Dropbox 或其他提供本地挂载目录的云盘，优先直接利用它们暴露出来的本地文件系统目录。




---




## 4. 什么叫完整同步




目标不是磁盘逐字节克隆，而是“协作完整的项目镜像”。




凡是对产品、工程、设计、测试、验收、恢复、历史追溯或后续协作有价值，并且适合进入共享环境的项目文件，默认都应该同步。




不要把“只同步 Git 已跟踪文件”当成唯一规则。




安全、有效、具有项目价值的未跟踪文件也可以进入共享镜像。




---




## 5. 默认同步范围




默认同步：




- 源代码；
- 测试；
- 脚本；
- 配置；
- lockfile；
- schema / contract；
- 正式 Markdown 文档；
- 设计资产；
- 脱敏后的测试夹具；
- 可共享的截图；
- 正式交接文件；
- 历史产品与工程文档；
- 发布与验收产物；
- 对评审、测试、恢复或交付有实际价值的生成文件；
- 其他安全且有协作价值的项目文件。




以下内容不要因为“是生成文件”就自动排除：




- dist/；
- 构建产物；
- 生成报告；
- 分析包；
- 发布包；
- 验收证据。




是否同步应按“有没有协作价值”判断。




---




## 6. 默认不同步范围




默认排除：




- .git/；
- node_modules/；
- 真实 .env；
- API Key；
- token；
- credential；
- 浏览器或 QA profile；
- cookie；
- session；
- MFA 后的会话状态；
- 私有原始业务数据；
- 含个人或业务隐私的原始截图；
- 原始推理轨迹；
- 纯缓存；
- 纯临时文件；
- 其他不适合进入共享环境的机器内部状态。




原因：




### .git/




Git 自己已经负责提交历史、对象、引用、锁和回滚。把 .git/ 放进云盘双向同步没有必要，而且在 Git 正在写入时可能出现冲突或损坏。




### node_modules/




体积大、小文件数量多、可通过 lockfile 重建，并且可能包含平台相关二进制。同步它通常只会拖慢系统。




### .env、凭据和会话状态




它们属于安全边界，不应该进入共享项目镜像。




### 私有原始数据




共享镜像会扩大可访问范围。只有经过脱敏、确认适合协作的数据才应该进入。




### 纯缓存和临时文件




它们变化频繁、可重新生成，而且会制造大量无意义的文件变化。




---




## 7. 文件同步与文件阅读是两件事

这是整套方法最重要的成本原则之一。

智能体不需要为了同步一个文件而阅读它的正文。日常交接也不需要重新扫描整个云端项目树。

**默认同步入口是 Handoff 中明确列出的 Changed Files。** 接收方只需要对这些路径做存在性、大小、修改时间、必要时 hash / 内容校验，并把它们定点复制到另一侧。

例如一个项目有 500 个文件，本轮 Handoff 明确列出 8 个 Changed Files：

```text
读取 Handoff → 得到 8 个路径 → 校验 / 复制这 8 个文件 → 完成
```

不需要为了证明另外 492 个文件没有变化而逐个打开它们。

文件同步成本与模型上下文成本应彻底分离；**云盘按需下载成本也应与逻辑项目规模分离。**

对于 Google Drive Desktop / OneDrive Files On-Demand / Dropbox Smart Sync 一类会把未本地化文件显示为 placeholder 的系统：

- 列目录不等于文件已经本地可用；
- 对 placeholder 做 hash、内容 diff、递归 rsync 等操作可能触发真实下载；
- 因此不得把“递归比较整个挂载目录”当作每次交接的默认同步方式。

模型只阅读真正需要理解的文件；文件系统也只下载本轮真正需要传输的文件。

---

## 8. 优先使用文件系统原生同步

如果云盘已经提供本地挂载目录，仍优先使用系统已有工具，但使用范围必须受 Handoff 的 Changed Files 约束：

- `cp`：定点复制明确文件；
- `rsync`：只对明确文件列表或明确的小范围目录使用；
- `diff` / `shasum`：只对已经需要同步的具体文件做校验；
- Git：检查 canonical local repo 的本地状态与工程差异。

不需要为了这套协作方式额外开发同步程序。

### 8.1 日常交接默认：Manifest-driven targeted sync

正常 Handoff：

```text
Sender 更新正式文件
→ Sender 在 Handoff 写明 Changed Files
→ Receiver 读取 Handoff
→ 定点同步 Changed Files
→ 在 canonical local repo 工作
```

如果 Handoff 没有 Changed Files 清单，接收方应停止同步并让发送方补齐，而不是自行扩大为整个项目树同步。

### 8.2 全项目一致性检查不是日常同步

只有以下情况才需要单独做全项目一致性审计：

- 第一次建立共享镜像；
- 怀疑 Shared Working State 已严重漂移；
- 迁移机器 / 云盘目录；
- 明确的恢复 / reconciliation 工作；
- Product Owner 明确要求。

即使需要全项目审计，也优先使用不会下载文件内容的 metadata、Drive API listing、已有本地 manifest 或 Git 信息。

**不得在 Files On-Demand 挂载目录上通过递归读取内容来“找差异”，从而无意 hydrate 整个云端镜像。**

---

## 9. 同步方向与修改权限




### 9.1 物理文件层面




项目文件可以：




云端共享镜像 ↔ 本地项目目录




双向同步。




### 9.2 修改权限层面




物理双向同步不等于所有智能体都可以修改所有文件。




推荐权限：




- 产品侧智能体：产品文档的主要维护者；
- 工程侧智能体：生产代码的主要维护者；
- 两侧都可以读取完整项目镜像；
- 混合文档由最接近事实的一侧提供事实，再由负责最终表达的一侧整理。




原则：




> 同步方向与修改权限分离。




---




## 10. 每次交接使用两个长期文件




不要每次新建一份交接文档。




推荐在项目中固定保存：




docs/collaboration/CHATGPT_TO_CODEX_HANDOFF.md
docs/collaboration/CODEX_TO_CHATGPT_HANDOFF.md




名称可以根据实际使用的智能体调整，但建议保持“发送方 → 接收方”的方向明确。




规则：




- 产品侧只更新“产品侧 → 工程侧”文件；
- 工程侧只更新“工程侧 → 产品侧”文件；
- 接收方读取对应文件；
- 每次新交接直接覆盖自己的长期交接文件；
- 不需要建立不断增长的临时 Handoff 文件。




---




## 11. 交接文件不是历史档案




长期交接文件的定位是：




> 当前收件箱，而不是历史档案。




它只负责告诉接收方：




- 当前处于什么阶段；
- 本轮发生了什么；
- 哪些文件发生变化；
- 哪些文件需要重点阅读；
- 同步方向是什么；
- 下一步任务是什么；
- 有什么约束；
- 验收标准是什么；
- 是否存在阻塞或冲突。




真正需要长期保存的事实应进入：




- 产品需求文档；
- 决策日志；
- 技术设计；
- AI 设计；
- 工程报告；
- 验收记录；
- Git history；
- 其他正式文档。




不要让 Handoff 变成第二套历史数据库。




---




## 12. 长期交接文件的固定结构




建议每份 Handoff 至少包含：




- Handoff ID；
- Updated At；
- From；
- To；
- Current Stage；
- Status；
- Source Git HEAD；
- 本轮发生了什么；
- **Changed Files / Sync Scope（必须明确列路径；这是默认物理同步清单）；**
- 接收方需要重点阅读；
- 同步要求；
- 下一步任务；
- 不要做什么；
- 验收要求；
- 已知问题 / 冲突；
- 其他说明。




Status 建议使用：




- READY；
- IN_PROGRESS；
- WAITING；
- BLOCKED。




接收方只执行最新且状态为 READY 的交接。




---




## 13. Handoff Prompt 可以缩短到一句话




当长期 Handoff 已经成为正式协作入口后，不再需要每轮复制长提示词。




产品侧交给工程侧时，只需要：




> 读取最新的“产品侧 → 工程侧” Handoff，按照其中指令继续。




工程侧交给产品侧时，只需要：




> 读取最新的“工程侧 → 产品侧” Handoff，按照其中指令继续。




真正的完整指令放在 Handoff 文件内部。




这可以显著减少人工复制、提示词重复、上下文丢失、错版本风险和交接时的 token 消耗。




---




## 14. Handoff 与同步的职责不同




Handoff 负责“语义：发生了什么，下一步要做什么”。




文件同步负责“物理：哪些文件需要从一边复制到另一边”。




不要让 Handoff 承担文件传输，也不要让 rsync 承担项目理解。




可以理解为：




- Handoff = 发生了什么；
- 文件系统同步 = 哪些文件不一样；
- 正式文档 = 事实是什么；
- Git = 历史发生过什么。




---




## 15. 产品侧 → 工程侧流程

```text
产品侧完成工作
→ 更新云端共享镜像中的正式文档
→ 在 Product → Engineering Handoff 明确列出 Changed Files
→ 产品负责人只发送一句“读取最新 Handoff”
→ 工程侧读取 Handoff
→ 只把 Changed Files 从 Drive 定点同步到 canonical local repo
→ 只重点阅读 Handoff 指定的文件
→ 开始工程工作
```

默认禁止为了这一步递归比较 / 同步整个 Google Drive 项目树。

如果某个未列出的文件是完成任务真正需要的依赖，而且 canonical local repo 中不存在或明确过期，工程侧可以**单文件追加同步**并在出站 Handoff 记录原因；不得借此扩大成全树同步。

---

## 16. 工程侧 → 产品侧流程

```text
工程侧完成开发和测试
→ 生成 Git diff / changed-file list
→ 更新“工程侧 → 产品侧”长期 Handoff，并明确 Changed Files
→ 只把 intended Shared Working State 中本轮 Changed Files 定点写回 Google Drive
→ 云盘客户端上传这些文件
→ 产品负责人只发送一句“读取最新 Handoff”
→ 产品侧按 Changed Files 读取必要文件
→ 产品评审或下一轮规划
```

不要把整个 canonical repo 无差别复制到 Google Drive 来代替 Changed Files manifest。

---

## 17. 增量同步与全量同步

### 17.1 日常默认：Changed Files 定点同步

每次 Handoff 默认只同步发送方明确列出的 Changed Files。

这既是**逻辑增量**，也是**物理增量**：不重新下载、比较或覆盖没有变化的文件。

### 17.2 全量的正确含义

“共享镜像应该最终完整”不等于“每轮都重新遍历 / 下载整个共享镜像”。

完整性由以下组合保证：

- 第一次初始化建立完整 baseline；
- Git 保存工程历史；
- 每次 Handoff 的 Changed Files 串联后续变化；
- 必要时才执行独立 reconciliation / full audit。

### 17.3 Files On-Demand 特别规则

Google Drive Desktop 等可能把云端文件以 placeholder 呈现。对整棵树执行以下操作可能导致大量真实下载，因此日常 Handoff 禁止：

- 递归 `rsync` 内容比较；
- 递归 hash / `shasum`；
- 递归内容 `diff`；
- 任何为了“找差异”而打开每个云端文件内容的脚本。

全项目 audit 如确有需要，应作为独立任务，并选择不会 hydrate 全树的 metadata 方法。

## 18. 冲突保护




同步前需要避免盲覆盖。




至少检查：




- 本地是否有未提交修改；
- 云端同名文件是否也发生变化；
- 文件 hash 是否不同；
- 当前 Git HEAD；
- Handoff 指定的同步方向。




如果双方都改了同一份文件：




> 停止自动覆盖，报告同步冲突。




再由高能力模型或产品负责人决定合并、保留本地、保留云端或手工处理。




删除操作尤其需要谨慎。




不要默认使用无条件 destructive --delete。




---




## 19. 安全与隐私检查




同步前优先使用确定性规则：




文件路径与类型 → 排除规则 → secret scan → privacy rule → 同步 → 校验。




不要让高能力模型为了判断“要不要同步”而逐份阅读整个项目。




如果发现 secret、token、credential 或 private raw data，停止同步对应内容，并报告路径和原因，但不要把敏感内容本身输出到日志或聊天。




---




## 20. Git 的职责




Git / GitHub 负责：




- diff；
- commit；
- branch；
- history；
- rollback；
- tag；
- release；
- public repository。




云端共享目录不替代 Git。




推荐理解：




日常共享工作状态 → 云端共享镜像。
版本与历史 → Git / GitHub。




不需要为了让产品侧智能体看到最新文件而频繁做无意义 commit。




---




## 21. 文档与事实治理




所有长期事实应该进入它真正所属的文档。




推荐遵循：




> 一个事实，一个权威归属。




例如：




- 产品要求 → 产品需求文档；
- 当前 AI 行为 → AI 设计；
- 技术结构 → 技术设计；
- 为什么这样决定 → 决策日志；
- 已实现和已测试什么 → 工程报告；
- 当前交接 → Handoff；
- 版本历史 → Git。




Handoff 不复制长期文档正文，只引用需要重点阅读的文件。




---




## 22. 新项目如何直接复用




任何新项目要采用本模式，只需要：




1. 建立 canonical local repo；
2. 建立云端项目文件夹；
3. 启用云盘桌面客户端；
4. 确定本地挂载路径；
5. 第一次建立协作完整镜像；
6. 放入本规范；
7. 在项目 Agent 规则入口中引用本规范；
8. 建立两个长期 Handoff 文件；
9. 确定默认排除规则；
10. 开始第一次产品侧 → 工程侧交接。




不需要：




- 新建同步服务；
- 新建数据库；
- 新建 daemon；
- 新建专用 API；
- 每轮打 ZIP；
- 每轮复制长 Prompt；
- 每轮重新上传整个仓库。




---




## 23. 推荐的项目规则入口




项目可以在 AGENTS.md 或等价规则文件中只写一个短入口：




> 跨智能体协作、云端共享镜像、文件同步与 Handoff 必须遵循项目中的《多智能体项目协作与共享镜像规范》。大规模文件传输优先使用云盘桌面客户端与本地文件系统工具，不使用高能力模型逐文件搬运。




详细规则只保留在本规范中，避免多个文件复制相同规则。




---




## 24. 什么时候需要人工介入




自动流程可以自行处理：




- 文件比较；
- 无冲突同步；
- 普通增量复制；
- hash 校验；
- 读取 Handoff；
- 自动测试。




需要人工介入：




1. 产品范围或边界变化；
2. 产品影响型技术冲突；
3. 双方修改同一文件产生冲突；
4. 关键测试失败且无法自行解决；
5. 发布或重大里程碑验收；
6. 安全、隐私或 secret 风险。




---




## 25. 最终工作模型




最终把整个协作理解成四层：




第一层：正式项目事实
代码 / 文档 / 测试 / 设计 / 证据




第二层：共享项目状态
云端共享镜像




第三层：当前交接
两个长期 Handoff




第四层：版本历史
Git / GitHub




不同智能体之间不再“搬一份上下文”，而是围绕同一个项目状态协作。




---




## 26. 最终原则




1. 一个项目状态：本地与云端代表同一个协作项目。
2. 完整但不盲目：尽可能同步有协作价值的文件。
3. 秘密不共享：secret、credential、session、private raw data 留在安全边界内。
4. 文件系统做传输：优先使用云盘桌面客户端与 rsync 等现成工具。
5. 模型不当搬运工：模型负责判断，不负责逐文件网络传输。
6. Handoff 驱动的物理增量：日常只同步明确 Changed Files；完整性由 baseline + 连续 Handoff + 必要时独立 audit 保证。
7. 同步与阅读分离：复制文件不等于把文件内容放进模型上下文。
8. 同步方向与修改权限分离：文件可双向同步，但代码和产品文档有不同维护责任。
9. 两个长期 Handoff：一个方向一个文件，每次覆盖当前状态。
10. Handoff 是收件箱，不是档案馆。
11. Prompt 极简化：交接时只需要“读取最新 Handoff 并继续”。
12. Git 管历史，云盘管共享状态，正式文档管事实。
13. 先用简单方法：没有真实痛点前，不开发新的同步基础设施。
14. 发生冲突时停止盲覆盖。
15. 让人只处理真正需要人的决策。




---




## 27. 核心结论




这套模式的本质不是“把项目备份到云盘”。




它真正解决的是：




> 如何让多个 AI Agent 围绕同一个项目持续协作，而不反复搬运上下文、文件和长提示词。




最佳分工是：




> 高能力模型做高价值思考，文件系统做文件传输，长期文档保存事实，Handoff 保存当前交接，Git 保存历史。




---




## 28. 如何进入这个协作闭环




这套协作模式需要区分“第一次建立项目”与“之后每一次进入项目”。




### 28.1 第一次建立新项目：需要一次启动提示




新项目第一次采用这套模式时，需要一条一次性的启动提示，用来完成以下初始化：




1. 找到或建立本地代码仓库；
2. 找到或建立云端共享项目目录；
3. 确认云盘桌面客户端的本地挂载路径；
4. 将本规范放入项目的长期文档目录；
5. 在项目的 Agent 规则入口中登记本规范；
6. 建立两个长期 Handoff 文件；
7. 建立第一次协作完整镜像；
8. 明确默认同步排除项；
9. 明确产品侧和工程侧的修改权限；
10. 完成第一次交接。




这条启动提示只用于“安装协作系统”，不应在每轮工作中重复。




推荐的新项目启动提示可以非常短：




> 为这个项目启用项目内《多智能体项目协作与共享镜像规范》。先建立云端共享镜像和本地同步关系，在 Agent 规则入口中登记协作规范，并创建产品侧 → 工程侧、工程侧 → 产品侧两个长期 Handoff。完成初始化后，所有后续交接都从长期 Handoff 进入，不再使用长交接 Prompt。




### 28.2 项目已经初始化：从 Agent 规则入口进入




项目一旦完成初始化，工程侧智能体每次进入仓库时，都应该先读取项目的 Agent 规则入口，例如：




`AGENTS.md`




其中只需要保留一条稳定入口规则：




> 开始跨智能体协作任务前，先读取项目中的《多智能体项目协作与共享镜像规范》，然后读取“发送给自己”的长期 Handoff；如果 Handoff 状态为 READY，则按其中要求完成同步并继续工作。




详细协作规则不要复制到 AGENTS.md，避免多个规则源漂移。




### 28.3 产品侧智能体的入口




如果产品侧智能体不会自动读取仓库中的 AGENTS.md，应在该产品侧工作空间、项目说明或第一次启动提示中加入一条长期入口：




> 每次开始项目工作前，先从云端共享项目目录读取《多智能体项目协作与共享镜像规范》，再读取“工程侧 → 产品侧”长期 Handoff。只有状态为 READY 的最新 Handoff 才作为本轮交接入口。




这条规则可以放进 ChatGPT Project Instructions、团队工作区说明或其他等价的持久项目设置中。




### 28.4 日常交接不再需要长 Prompt




完成初始化以后，正常交接只需要一句话：




产品侧 → 工程侧：




> 读取最新的“产品侧 → 工程侧” Handoff，按照其中指令继续。




工程侧 → 产品侧：




> 读取最新的“工程侧 → 产品侧” Handoff，按照其中指令继续。




如果接收方已经通过持久项目规则自动知道 Handoff 位置，甚至可以进一步缩短为：




> 读取最新 Handoff，继续。




---




## 29. 每次新会话的标准启动顺序




无论是哪一侧，进入一个已经初始化的项目时，标准顺序都是：




1. 读取项目规则入口；
2. 读取本协作规范；
3. 确定自己是产品侧还是工程侧；
4. 读取“发送给自己”的长期 Handoff；
5. 检查 Handoff ID、更新时间、状态和源项目状态；
6. 如果状态不是 READY，不自行猜测下一步；
7. 如果状态是 READY，先按 Handoff 的 Changed Files / Sync Scope 做定点同步；
8. 只重点读取 Handoff 指定的文件；不得为了同步而递归 hydrate 云端项目树；
9. 开始本轮正式工作；
10. 工作完成后更新“自己发送给对方”的长期 Handoff。




这形成一个稳定闭环：




规则入口
→ 协作规范
→ 入站 Handoff
→ 同步
→ 工作
→ 出站 Handoff
→ 对方的规则入口。




---




## 30. 为什么仍然保留启动 Prompt




长期 Handoff 可以消灭“每轮长 Prompt”，但不能完全消灭“第一次入口”。




原因是：




- 一个全新的 Agent 还不知道项目在哪里；
- 它还不知道协作规范在哪里；
- 它还不知道自己应该读取哪个 Handoff；
- 一个全新的项目也还没有建立共享镜像和长期 Handoff。




因此最佳设计不是“永远不要 Prompt”，而是：




> **一次性 Bootstrap Prompt + 持久 Agent 入口 + 两个长期 Handoff + 日常一句话交接。**




其中：




- Bootstrap Prompt 负责安装协作系统；
- Agent 规则入口负责告诉智能体从哪里开始；
- Collaboration Model 负责解释整套规则；
- Handoff 负责当前任务；
- 云端镜像负责共享文件状态；
- Git 负责历史。




完成第一次初始化后，后续绝大多数交接都不再需要复制长 Prompt。


---


## 31. 项目内协作与独立协作系统的边界


这套协作方法可以被视为一个独立的方法与工具项目，但它同时会被具体产品项目真实使用。两者必须分开治理，不能因为后续要把协作系统独立出来，就删除具体项目已经依赖的协作规则和入口。


### 31.1 项目内必须保留的部分


一个实际采用本模式的产品项目，应继续保留它运行协作闭环所需要的项目内文件，例如：


- 项目内的协作规则入口；
- 项目内的 `AGENTS.md` 或等价规则入口；
- `docs/collaboration/CHATGPT_TO_CODEX_HANDOFF.md`；
- `docs/collaboration/CODEX_TO_CHATGPT_HANDOFF.md`；
- 与该项目实际同步、权限、冲突保护有关的必要规则；
- 项目版本自身的方向调整记录、技术设计、工程报告和验收记录。


这些内容属于“该项目如何实际使用协作系统”，不能因为协作系统后来成为独立项目而从项目中清空。


### 31.2 独立协作系统负责的部分


以下内容属于协作系统自身的研究与评估，不应混入具体产品版本的 PRD、AI Design、Interaction Spec、Technical Design 等产品文档：


- ChatGPT、Codex、Google Drive 与本地 Git 的实际协作过程记录；
- Codex 模型与推理模式记录；
- Codex quota / 用量快照与阶段消耗；
- Product Owner 直接干预次数及其对返工、用量的影响；
- 文件同步数量、同步方向、冲突与耗时；
- 重复上下文读取情况；
- Handoff 是否减少人工搬运和长 Prompt；
- 跨项目可复用的协作方法评估；
- 最终的通用模板、指标体系与方法论。


这些内容后续应进入独立的协作系统项目。具体产品项目只保留它实际采用该系统所必需的入口和项目自身事实。


### 31.3 当前试点阶段


在独立协作系统项目正式抽离之前，本文件仍然是当前项目实际协作的规则基线。


试点结束后，可以把通用规则、评估方法和模板迁移到独立协作系统项目；但具体项目仍应保留运行所需的项目内规则、双向 Handoff 与必要引用，不做“全部删除式”的抽离。

## 32. v0.3.0 协作试点的过程记录


v0.3.0 不只验证产品开发结果，也用于验证整套协作闭环是否值得长期采用。


试点至少完整覆盖：


```text
Product Planning
→ Product Handoff
→ Drive → Local Sync
→ Engineering
→ Local → Drive Sync
→ Engineering Handoff
→ Product Review
```


过程记录必须以真实发生的行为为准，而不是事后凭印象回忆。


### 32.1 ChatGPT 侧记录


产品侧应记录：


- 本轮从 Google Drive 实际读取了哪些权威文件；
- 哪些文件通过 Handoff 被指定为重点阅读；
- 是否需要重新读取整个项目，还是只读取 Changed Files / Authoritative Files；
- 哪些产品文档由 ChatGPT 直接更新；
- 是否出现文档版本不一致、旧快照误读或重复读取；
- 每次 Product → Engineering 交接实际生成或更新了哪些文件。


原则：


> ChatGPT 可以实时读取 Google Drive 中的最新共享状态；不要求先把整个项目下载到本地，也不应无目的地重新读取整个 repository。


### 32.2 Codex 侧记录


工程侧应记录：


- 入站 Handoff；
- Drive → Local 实际同步方式；
- 实际同步的 Changed Files；
- 本地重点读取的文件；
- 是否发生不必要的全仓重复读取；
- 实现、测试和调试阶段；
- Local → Drive 实际同步结果；
- 出站 Handoff；
- 同步冲突、阻塞和异常；
- 是否发生 Files On-Demand placeholder 被意外批量 hydrate / download。


原则：


> Codex 优先按入站 Handoff 的 Changed Files 把需要的最新变化定点同步到 canonical local repo，再以本地文件与 Git 为主要工程工作面；完成后仅把出站 Handoff 列出的本轮 Changed Files 定点同步回 Google Drive。


文件传输本身不要求模型阅读文件正文。


---


## 33. Codex 用量与 quota 观测规则


协作试点必须记录 Codex 的实际用量，不能只靠“感觉更省 token”。


### 33.1 每个 Codex 工作单元的基本快照


每次开始一个相对独立的 Codex 工作单元前，由 Product Owner 提供：


- 当前工作阶段；
- 本轮任务；
- 使用模型；
- 推理模式；
- Codex UI 当时显示的 quota / 剩余额度 / 用量数值；
- 该数值的原始口径和单位。


工作单元结束后，再提供一次相同口径的数值。


产品侧据此记录：


- 开始快照；
- 结束快照；
- 本轮差值；
- 模型；
- 推理模式；
- 任务产出；
- 是否返工；
- 是否发生额外同步或重复读取。


不要在 UI 口径不明确时自行换算成绝对 token 数。优先保存用户实际看到的原始数值和单位。


### 33.2 需要增加中间快照的情况


出现以下任一情况时，应考虑增加一次中间用量快照：


- Product Owner 直接向 Codex 发出明显改变方向的指令；
- 模型发生切换；
- 推理模式发生切换；
- 从分析进入实现、从实现进入大规模测试等明显阶段边界；
- 出现大规模返工；
- 出现异常的重复读取、调试或测试；
- 单次工作持续很长，若只记首尾会无法判断成本来源。


### 33.3 记录目标


最终至少能够回答：


- 一次完整 Product → Engineering → Product 闭环消耗多少 Codex quota；
- 哪个阶段最耗；
- 不同模型与推理模式的消耗差异；
- Handoff 是否减少重复上下文读取；
- 文件系统增量同步是否降低模型搬运成本；
- Product Owner 的中途干预是否显著增加返工和消耗；
- 哪些步骤应在后续流程中继续、调整或取消。


---


## 34. Product Owner 直接干预记录


Product Owner 在 Codex 工作期间可以直接调整方向。为了评估协作效率，这些干预必须被记录，但不能和产品版本的方向调整历史混为一谈。


### 34.1 Codex 在出站 Handoff 中记录


`CODEX_TO_CHATGPT_HANDOFF.md` 在每个工程工作单元结束时，应增加本轮 Product Owner Direct Intervention 摘要，至少记录：


- 是否发生直接干预；
- 干预发生在哪个阶段；
- 指令摘要；
- 干预原因（如果 Product Owner 明确提供）；
- 是否改变原 Handoff 的任务范围或实现方向；
- 是否造成返工；
- 影响了哪些工作或文件；
- 是否伴随模型 / 推理模式变化；
- 对应的产品方向调整 ID（如果存在）。


Codex 只记录事实，不自行推断某次干预“消耗了多少 quota”。


### 34.2 Handoff 不是长期用量档案


Handoff 仍然是当前收件箱，会被后续交接覆盖。


因此，在下一次覆盖 `CODEX_TO_CHATGPT_HANDOFF.md` 之前，产品侧应把需要长期评估的干预摘要和用量数据转入独立协作系统的 Pilot / Usage Record。


---


## 35. Direction Adjustments、Handoff 与用量记录必须分开


三个记录系统职责不同，不得合并为同一份文档。


### 35.1 Direction Adjustments


具体产品项目的 `DIRECTION_ADJUSTMENTS_vX.Y.Z.md` 记录：


- Product Owner 在开发开始后的产品或工程方向调整；
- 调整原因；
- 覆盖或修正了什么旧方向；
- 最终实际改动；
- 对产品定义、交互、技术边界或验收的影响。


它属于具体产品版本历史。


### 35.2 双向 Handoff


双向 Handoff 记录：


- 当前阶段；
- 本轮发生了什么；
- Changed Files；
- 重点阅读文件；
- 同步要求；
- 下一步任务；
- 阻塞 / 冲突；
- 本轮直接干预摘要。


它属于当前协作状态，不是历史数据库。


### 35.3 Collaboration Pilot / Usage Record


独立协作系统的 Pilot / Usage Record 记录：


- Codex 模型；
- 推理模式；
- 开始 / 结束 quota；
- 阶段消耗；
- 中间快照；
- 直接干预次数；
- 是否返工；
- 文件同步数量；
- 重复读取；
- 同步冲突；
- 协作效率评估。


它属于协作系统研究数据，不属于具体产品版本的产品事实。


### 35.4 同一次事件的关联方式


同一次 Product Owner 调整如果同时影响产品方向和协作成本，两边都要记录，但不复制完整正文。


推荐：


```text
Direction Adjustment: DA-003
        ↕
Collaboration Intervention Event: INT-003
```


产品版本记录“改了什么、为什么改”；协作系统记录“这次干预发生在什么时候、是否返工、对用量观测有什么影响”。

## 36. 协作试点的评估边界


具体产品是否开发成功，与协作系统是否高效，是两个独立结论。


产品验收关注该产品自身的功能、质量、性能和用户价值。


协作系统评估关注：


- Codex quota / token 成本；
- Product Owner 人工搬运量；
- 直接干预次数；
- 返工次数；
- Handoff 清晰度；
- 文件同步效率；
- 重复读取情况；
- 同步冲突；
- 上下文恢复成本；
- ChatGPT ↔ Codex 状态一致性。


不得因为产品最终 PASS 就自动判定协作系统 PASS，也不得因为协作流程存在摩擦就否定产品本身。


试点结束后，基于真实数据决定：


1. 哪些规则继续作为具体项目内协作基线；
2. 哪些通用部分抽离到独立协作系统项目；
3. 哪些流程需要简化；
4. 是否需要新的自动化；
5. 哪些步骤仍应保持人工决策

## 37. 正式文档写回：本地修改 → 整文件上传替换（强制）

本节是日常正式文档编辑的**固定规则**，不是可自由选择的效率建议。这里的“本地”指执行本轮编辑的 Agent 可访问的本地文件工作区（如 ChatGPT 文件工作区或 Codex 的本地仓库），不要求 Product Owner 手工搬文件；“云端”指 Google Drive Shared Working State。

### 37.1 适用范围与禁止事项

对项目正式仓库文档，特别是 Markdown（`.md`），以及需要维护为原生文件的纯文本、JSON 和配置文档，统一采用：**先下载或读取最新文件 → 本地修改完整文件 → 本地检查 → 上传覆盖原 Drive 文件 → 云端回读验证**。

- **禁止在 Google Drive 在线界面或通过远端文档编辑接口直接逐段修改、插入或替换正式仓库 Markdown 文档。**
- **禁止跳过本地文件成稿、diff/格式/内容校验，直接在云端原文件上做编辑。**
- 不以每轮新建同名 Handoff、临时副本或 Google Docs 转换件来代替覆盖原文件；必须保留同一正式文件的相对路径、文件名、Markdown 格式及原 Drive 文件 ID。
- 如果当前工具不能安全替换原文件，**STOP 并报告具体阻塞，不能把云端直接编辑作为默认回退方案**。可以在有冲突保护的前提下使用上传中转文件，但最终必须替换原始 ID，校验完成后清理临时文件。

### 37.2 标准写回步骤

```text
确认最新入站 Handoff / Changed Files 和文件 authority
→ 读取 / 下载 Drive 当前正式原文件
→ 在本地工作区修改完整文件（不要线上逐段编辑）
→ 本地检查正文、格式、diff、路径和必要的交叉引用
→ 上传完成稿，安全替换 Drive 中同一原文件（保留 file ID）
→ 重新从 Drive 读取正式原文件，确认内容 / hash / 版本正确
→ 在出站 Handoff 的 Changed Files / Sync Manifest 记下这次改动
→ 由接收方按 Manifest 定点同步到 canonical local repo
```

上传之前要确认 Drive 原文件在下载之后没有被其他智能体修改，并遵守第 18 节的冲突保护、权限和隐私规则。云端与本地出现同名文件不同改动时不得盲覆盖。删除和大范围同步依旧需要专门检查。

### 37.3 Google 原生 Docs / Sheets / Slides 的边界

本项目的正式仓库文档仍是 Markdown，不将正式 Markdown 转换为 Google Docs 再编辑。原生 Google Docs / Sheets / Slides 只在用户**明确指定该类原生文件任务**时使用对应原生接口；这不是正式 Markdown 文档的回退路径，也不能用原生在线编辑代替上述上传替换流程。

### 37.4 协作效率与记录

这个约束的目的是减少细碎云端写操作，降低延迟与半成品覆盖风险，同时保留清楚的本地 diff 和云端校验结果。协作试点需要记录本轮本地修改、整文件上传、回读校验、冲突或失败情况；不再将“在线逐段编辑”视为正式 Markdown 文档的可选正常路径。
